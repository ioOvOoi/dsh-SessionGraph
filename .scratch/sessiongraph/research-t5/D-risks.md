# T5 技术风险与边界分析

> 边界/风险分析员产出 · 2026-08  
> 针对 T5:同会话跳转切枝 + B1 compaction 式遮蔽  
> 只读分析,不修改代码

## 10 行内摘要

| # | 要点 |
|---|------|
| 1 | **自动压缩 × 手动遮蔽叠加**是最核心风险:嵌套/重叠 replace 可能导致投影事件范围冲突,需明确"段编号递增+单调不回退"策略 |
| 2 | **运行中切 active** 是高风险操作:turn 未完成时遮蔽会导致 surface 破裂、模型上下文不一致;必须禁止或强制等 turn/end |
| 3 | **多 agent(subagent)会话**:子 agent 是独立会话,父会话切枝不应联动子会话 active;switch 节点的遮蔽需特殊处理(委派记录独立于消息段) |
| 4 | **摘要粒度**:需平衡"足够信息量"与"上下文窗口压力";建议摘要包含条数+首尾消息+用户意图标签 |
| 5 | **冷启动/重建**:投影 v5 的 stateVersion 机制能兼容,但需验证 replace 事件在重放时的正确性 |
| 6 | **不做 T5 的后果**:上下文污染无法回避,演示路径"点击跳转→继续对话→模型回答被旧分支污染"是体验硬伤 |
| 7 | **退化方案**:B1 不可退化为 B2(已否决);可退化为"仅视觉遮蔽(不触发真实 compaction)"——但这等于放弃上下文隔离 |
| 8 | **性能边界**:频繁跳转(10+次)导致 replace 段累积,投影重放开销线性增长;需设上限或清理策略 |
| 9 | **误触恢复**:遮蔽一旦触发不可逆(日志 append 了 replace 事件);需二次确认+撤销日志(新 append 反向操作) |
| 10 | **平台 API 依赖**:B1 依赖 `session.deriveMessages()` 对 replace 的响应行为;需验证"replace 之后的下一次 deriveMessages 是否正确排除被遮蔽段" |

## 详细风险表

### 风险 1: 自动压缩 × 手动遮蔽叠加

| 维度 | 分析 |
|------|------|
| **场景** | DSH 自动 compaction 触发时,若已有 T5 手动遮蔽段存在,两者的 SurfaceOp replace 段可能重叠或嵌套 |
| **风险级别** | 🔴 高 |
| **具体问题** | ① 嵌套 replace:手动遮蔽段 [seq 10,20] 与自动压缩段 [seq 8,25] 重叠,投影在处理时需决定"段内段"的显示层级;② 摘要叠加:两段各自有摘要,图谱上可能出现"摘要节点被另一个摘要覆盖"的情况;③ 模型上下文:`deriveMessages()` 对两段 replace 的处理是否一致、是否会双重遮蔽导致信息丢失 |
| **规避建议** | ① **段编号单调递增**:每个 replace 段带唯一编号(从 1 递增),投影按编号顺序处理,不支持真正的嵌套——后发段必须完全包含在前段之外,或与前段相邻(不可交叉);② **自动压缩触发时检查现有段**:若自动压缩与已有手动段交叉,投影应合并为一个更大的遮蔽段;③ **图谱显示**:嵌套段用嵌套缩进(灰色条)而非覆盖;摘要节点显示为"摘要(来源:自动/手动)" |

### 风险 2: 切 active × 运行中 turn

| 维度 | 分析 |
|------|------|
| **场景** | 用户在 agent 正在回答/跑工具时,点击历史节点触发"跳转到此" |
| **风险级别** | 🔴 高 |
| **具体问题** | ① turn 未完成时,当前 turn 的部分消息已 append 到日志但 surface 不完整;遮蔽"被放弃的分支段"时,边界 seq 不明确;② 模型上下文不一致:agent 可能在 turn 中途收到新指令(切 active),导致回复逻辑混乱;③ 投影在 turn/start 后、turn/end 前处于不稳定状态,遮蔽事件可能触发额外的重渲染/状态翻转 |
| **规避建议** | ① **禁止运行中切换**:在 turn/start 到 turn/end 之间,禁用"跳转到此"按钮(按钮灰显+tooltip 提示"等待当前回复完成");② **延迟队列**:若用户在 turn 中点击,排队到 turn/end 后自动执行;③ **状态检测**:投影监听 turn/start 和 turn/end 事件,维护 `turnInProgress` 标志,Client 端据此控制按钮可用性 |

### 风险 3: 多 agent(subagent)会话

| 维度 | 分析 |
|------|------|
| **场景** | 父会话内切枝时,子 agent 会话的 active 状态如何处理;switch 节点(委派)与遮蔽段的关系 |
| **风险级别** | 🟡 中 |
| **具体问题** | ① 子 agent 是独立会话,有自己的日志和投影;父会话切枝不应联动子会话(它们是独立的时间线);② switch 节点(委派)本身是父会话中的工具调用+子会话记录;若 switch 节点所在的父会话段被遮蔽,子会话记录如何显示;③ 子会话可能仍在运行(后台 subagent),父会话切枝后子会话的"运行中"状态是否在图谱上保留 |
| **规避建议** | ① **子会话独立**:父会话切枝不影响子会话的 active;子会话有自己的 activeCursor(独立于父会话);② **switch 节点不可遮蔽**:switch 节点作为"委派记录"应独立于消息段,即使父会话段被遮蔽,switch 节点仍保留在图谱上(灰色/折叠但可展开);③ **子会话状态联动显示**:父会话图谱上 switch 节点的 tooltip 显示子会话的"运行中/已完成/失败"状态(已有实现:pkg-62.client.js L654) |

### 风险 4: 摘要粒度与信息损失

| 维度 | 分析 |
|------|------|
| **场景** | 遮蔽摘要应包含什么信息,如何平衡信息量与上下文窗口压力 |
| **风险级别** | 🟡 中 |
| **具体问题** | ① 摘要太简(仅条数):模型无法从摘要中恢复旧分支的语义;② 摘要太详(全文摘录):占用上下文窗口,且与原文重复;③ 原文可恢复性:事件日志保留原文(平台事实),但用户如何查看被遮蔽段的原文 |
| **规避建议** | ① **摘要格式建议**:条数 + 首条用户消息(截断 50 字) + 末条助手消息(截断 50 字) + 用户意图标签(如"讨论了 X 问题");② **原文恢复**:图谱上遮蔽段显示为"已折叠·N 条",点击可展开查看原文(不恢复模型上下文,仅视觉展示);③ **事件日志保留**:平台保证原文在日志中保留(shadowed/log-only),投影只负责遮蔽 surface,不删除日志 |

### 风险 5: 冷启动/重建

| 维度 | 分析 |
|------|------|
| **场景** | 会话重启后,投影重建时遮蔽段与 replace 段是否仍能正确呈现 |
| **风险级别** | 🟡 中 |
| **具体问题** | ① 投影 v5 的 `stateVersion: 5` 在重建时会从头重放所有事件;replace 事件是否在重放时正确应用;② 若 replace 事件的 `start/end` 指向的 seq 在重放时尚未到达,是否会导致"段越界";③ 多次跳转后,replace 段累积(10+个),投影重建的计算开销 |
| **规避建议** | ① **replace 事件延迟应用**:投影在重放时,replace 段先缓存,等所有消息事件重放完成后再统一应用(类似数据库的"WAL 重放");② **段编号校验**:重建时校验 replace 段的 start/end 是否在有效 seq 范围内,异常段跳过并记录警告;③ **性能预估**:10 个 replace 段 × 平均 20 条消息 = 200 条消息需要遍历检查,开销可控(投影 stateVersion 机制保证增量更新,非每次全量重建) |

### 风险 6: 不做 T5 的后果

| 维度 | 分析 |
|------|------|
| **场景** | 维持现状(点击仅定位)的风险与机会成本 |
| **风险级别** | 🟢 低(但机会成本高) |
| **具体问题** | ① 当前"点击仅定位"无法实现用户核心需求"跳转后继续对话且不被旧分支污染";② 用户若在跳转后继续对话,模型上下文包含旧分支全部消息,回答质量下降;③ 演示路径"跳转→继续→新分支"在没有 B1 时无法干净实现 |
| **规避建议** | ① **不建议放弃 T5**:这是用户核心需求(Pi /tree 式跳转),放弃等于退化为"只读图谱";② **退化方案(仅当 B1 不可落地时)**:B2 已否决(上下文污染);唯一剩余选项是"视觉遮蔽+不触发真实 compaction"——图谱上显示遮蔽态但模型上下文不变,仅作为"历史标记"用途;③ **最低可行方案**:若时间紧张,先做"运行中禁止切换+遮蔽段图谱显示",推迟真实 compaction 触发 |

### 风险 7: 误触恢复与不可逆性

| 维度 | 分析 |
|------|------|
| **场景** | 用户误触"跳转到此"后,replace 事件已 append 到日志,无法真正撤销 |
| **风险级别** | 🟡 中 |
| **具体问题** | ① 日志是 append-only,replace 事件一旦写入无法删除;② 虽然可以再 append 一个"反向 replace"来恢复,但增加了日志复杂度;③ 用户可能误触多次,导致日志中累积大量 replace 事件 |
| **规避建议** | ① **二次确认**:点击节点 → 弹出确认"跳转到此将遮蔽 N 条消息,确定?"→ 确认后才执行;② **撤销机制**:支持"撤销上次跳转"(append 一个反向 replace,恢复被遮蔽段);③ **跳转历史**:记录跳转历史,用户可回溯到任意历史状态;④ **replace 段上限**:单会话最多 20 个 replace 段,超过后提示"建议清理旧遮蔽段" |

### 风险 8: 平台 API 依赖与行为不确定性

| 维度 | 分析 |
|------|------|
| **场景** | B1 依赖 `session.deriveMessages()` 对 replace 的响应行为,以及 session/event 流中 replace 事件的格式 |
| **风险级别** | 🟡 中 |
| **具体问题** | ① `deriveMessages()` 是否保证"replace 之后的调用排除被遮蔽段"?平台事实说"被 replace 遮蔽的段不进模型上下文",但未明确 API 行为;② replace 事件是否经 session/event 流出?平台事实说"compaction 事件经 session/event 流出",但 replace 本身是否是独立事件;③ 若平台行为变化(如 replace 格式变更),投影需适配 |
| **规避建议** | ① **验证平台行为**:实现前必须用 `sessiongraph_debug` 工具验证:在实际会话中触发一次 replace,检查 `deriveMessages()` 输出是否排除被遮蔽段;② **事件格式探测**:监听 session/event 流,记录 replace 事件的完整结构,作为投影实现的输入;③ **防御性编程**:投影中 replace 事件处理加 try-catch,异常时跳过该段并记录警告 |

### 风险 9: 投影 stateVersion 兼容性

| 维度 | 分析 |
|------|------|
| **场景** | 投影从 v5 升级到支持 T5 时,现有会话的 stateVersion 如何处理 |
| **风险级别** | 🟢 低 |
| **具体问题** | ① 若将 stateVersion 从 5 升到 6,现有会话的投影缓存会失效并重建;② 重建过程是否正确处理旧事件(无 replace 段的情况) |
| **规避建议** | ① **兼容升级**:新投影代码应同时处理 v5 和 v6 事件,用 stateVersion 区分;② **平滑迁移**:首次加载旧会话时自动重建,无用户感知;③ **测试覆盖**:确保"无 replace 段的会话"在新投影中正常显示 |

### 风险 10: 性能边界

| 维度 | 分析 |
|------|------|
| **场景** | 频繁跳转(10+次)导致 replace 段累积,投影重放开销线性增长 |
| **风险级别** | 🟢 低(原型阶段可忽略) |
| **具体问题** | ① 每个 replace 段在投影重放时需要遍历消息列表检查边界;② 10 个段 × 平均 20 条 = 200 条检查,开销可控;③ 长会话(1000+消息)时,重放时间可能从 <100ms 增长到 >500ms |
| **规避建议** | ① **replace 段索引**:投影维护 replace 段的有序索引(按 start seq),重放时用二分查找定位;② **增量更新**:非每次全量重建,仅在新事件到达时增量处理;③ **远景 fog**:自动压缩策略会合并旧段,控制段数量上限 |
